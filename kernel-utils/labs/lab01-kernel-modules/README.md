# Lab 01. 커널 모듈 입문

커널 모듈을 빌드하고 적재하면서 모듈의 생명주기, 커널 로그, 빌드 설정, oops 분석을 익힙니다.

- 원문: [UPB SO2 Lab 01 - Introduction](https://linux-kernel-labs.github.io/refs/heads/master/so2/lab1-intro.html)
- 스켈레톤 출처: [linux-kernel-labs/linux](https://github.com/linux-kernel-labs/linux) `a251a60`의 `tools/labs/templates/kernel_modules` (GPL-2.0)
- 원본은 Linux 5.10.14 기준이고, 이 실습 환경은 Linux 5.15.2입니다.

## 공통 절차

모든 명령은 Ubuntu VM의 `kernel-utils/`에서 실행합니다. 커널 빌드(`make kernel`)가 끝나 있어야 합니다.
아래 예시의 `<문제>` 자리에 `1-2-test-mod`처럼 문제 디렉토리 이름을 넣습니다.

```bash
make lab LAB=lab01-kernel-modules/<문제>   # 모듈 빌드 후 게스트로 전달할 파일 준비
make update-image                          # 첫 부팅이면 make image
make boot
```

게스트에 `root` / `kernel`로 로그인한 뒤 해당 디렉토리로 이동합니다.

```bash
cd /root/labs/lab01-kernel-modules/<문제>
```

코드를 고쳐 다시 빌드할 때는 게스트에서 `poweroff`로 QEMU를 종료한 뒤 위 절차를 반복합니다.

## 0. 코드 탐색 (코드 작성 없음)

**목표:** `linux-5.15.2/` 소스에서 아래 심볼의 정의를 찾습니다.

**확인할 것**
- `module_init`, `module_exit`은 무슨 일을 하는가? `init_module`, `cleanup_module`은 무엇인가?
- `ignore_loglevel` 변수는 무엇에 쓰이는가?

## 1. 커널 모듈 (`1-2-test-mod`, 실행·관찰)

**목표:** 모듈을 적재·확인·제거하고 메시지를 확인합니다.

**할 일**
1. `insmod`로 모듈을 적재합니다.
2. `lsmod`로 모듈이 목록에 있는지 확인합니다.
3. `rmmod`로 모듈을 제거합니다. 이때 확장자 없이 모듈 이름만 쓸 수 있습니다.
4. `dmesg`로 적재·제거 시의 메시지를 확인합니다.

**확인할 것:** 초기화 함수와 종료 함수는 각각 언제 호출되는가?

## 2. Printk (`1-2-test-mod`, 실행·관찰)

**목표:** 메시지가 시리얼 콘솔에는 나오지 않고 `dmesg`로만 보이게 설정합니다.

**할 일**
1. 모듈을 적재·제거하면서 메시지가 콘솔에 바로 출력되는지 관찰합니다. 출력되지 않으면 콘솔 로그 수준을 올려 출력되는 상태를 먼저 만듭니다.
2. `/proc/sys/kernel/printk`로 콘솔 로그 수준을 바꿉니다.
3. 모듈을 다시 적재·제거합니다.

**확인할 것:** 콘솔 출력과 `dmesg` 출력은 어떻게 달라지는가? 어떤 값을 썼고, 왜 그 값인가?

## 3. 오류 수정 (`3-error-mod`, 코드 수정)

**목표:** 컴파일 오류의 원인을 찾아 고칩니다.

처음에는 `make lab`이 **실패하는 것이 정상**입니다.

**확인할 것:** 왜 컴파일 오류가 나는가? `1-2-test-mod`와 무엇이 다른가?

수정 후 빌드하고 적재·제거까지 확인합니다.

## 4. 여러 소스 연결 (`4-multi-mod`, Kbuild 작성)

**목표:** `mod1.c`와 `mod2.c`를 하나의 모듈로 빌드합니다. `Kbuild`의 TODO를 채웁니다.

풀기 전에는 `Kbuild`에 빌드 대상이 없어 `.ko` 파일이 생기지 않습니다.

**확인할 것:** 적재·제거 시 메시지가 올바르게 출력되는가?

## 5. Kernel oops (`5-oops-mod`, Kbuild 수정·분석)

**목표:** oops가 발생한 주소를 찾고, 어떤 명령어가 원인인지 밝힙니다.

**할 일**
1. `oops_mod.c`를 읽고 어디서 문제가 생길지 예상합니다.
2. `Kbuild`의 TODO에 맞춰 디버그 정보 컴파일 플래그를 추가합니다.
3. 모듈을 적재하고 oops 메시지에서 명령어 포인터 값(x86-64에서는 `RIP`)을 찾습니다.
4. `/proc/modules`에서 모듈의 적재 주소를 확인합니다.
5. Ubuntu VM에서 `objdump`나 `addr2line`을 `oops_mod.ko`에 사용해 원인 명령어를 찾습니다.
6. 모듈 제거를 시도합니다.

**확인할 것:** 어떤 명령어가 oops를 일으켰는가? 모듈이 제거되지 않는 이유는 무엇인가?

이 문제는 `make boot`로 실행합니다. `make debug`는 `oops=panic` 옵션을 쓰므로 oops가 곧바로 패닉으로 이어집니다.
모듈이 제거되지 않으면 게스트를 재부팅해 다음 문제로 넘어갑니다.

## 6. 모듈 매개변수 (`6-cmd-mod`, 실행·관찰)

**목표:** 소스를 고치지 않고 `Early bird gets tired`가 출력되도록 모듈을 적재합니다.

먼저 그대로 적재·제거해 기본 메시지를 확인합니다.

**확인할 것:** 매개변수는 소스의 어디에서 선언되는가? 전달한 값은 메시지를 어떻게 바꾸는가?

## 7. 프로세스 정보 (`7-list-proc`, 코드 작성)

**목표:** `TODO`를 채워 현재 프로세스의 PID와 실행 파일 이름을 출력합니다. 모듈 적재 시와 제거 시 모두 출력해야 합니다. 적재 시에는 전체 프로세스의 PID와 이름도 출력합니다.

**참고:** `struct task_struct`의 정의를 찾아보세요. 현재 프로세스는 `current`로 가리킵니다.

**확인할 것:** 적재·제거를 반복하면 PID가 달라지는 이유는 무엇인가? 각각 어떤 실행 파일 이름이 출력되는가?
